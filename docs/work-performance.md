# MacのChatGPTアプリからSSHでEC2を計測・改善する

[構築・SSH接続](setup.md)の完了後、MacのChatGPTアプリのWorkで指示し、MacのシェルからSSHでEC2を操作する手順です。個人契約のPlusで、アプリにローカルWorkが表示され、シェルを利用できる環境を想定します。

| 場所 | 役割 |
| --- | --- |
| MacのChatGPTアプリ（Work） | 指示、結果確認、追加指示 |
| Macのローカルシェル | MacにあるSSH設定と鍵でEC2に接続 |
| EC2 | アプリ編集、サービス操作、ログ取得 |
| ベンチホスト | ベンチ実行と結果保存（別途準備） |

操作はMacアプリの同じWorkチャットで続けます。この手順では、Web版との実行環境の共有、Work Cloudの管理設定、MCPやプラグインの追加は必要ありません。EC2にCodex CLIを導入する必要もありません。

## 1. MacアプリでローカルWorkを選ぶ

1. MacのChatGPTアプリを起動し、**新しいチャット → Work** を開く。
2. 入力欄のすぐ下、右端の **ノートPCの形のアイコン** をクリックする。
3. 「このチャットをどこで実行しますか？」で **お使いのコンピューターで** を選ぶ。
4. 次の指示で、Mac上のシェルとSSHクライアントが使えることを確認する。

> Macのシェルでhostnameとpwdを実行し、command -v sshでSSHクライアントを確認してください。まだ外部接続やファイル変更は行わないでください。

「クラウドで」は選びません。設定項目の表記や配置はアプリのバージョンで変わる場合があります。ローカル実行やシェルが使えない場合は、その状態を確認してから進めます。権限の要求が出た場合は、対象の操作を確認してください。

## 2. MacからEC2へのSSHを準備する

[設定例](../config/ssh_config.example)を確認し、PCの `~/.ssh/config` に追記します。ファイル全体を上書きせず、HostNameをCloudFormation出力のPublicIpに置き換えてください。MacのOpenSSHを使う例です。

```bash
chmod 600 ~/.ssh/config
ssh isucon-practice
```

初回はホスト鍵の指紋を確認します。鍵にパスフレーズがある場合はPCのssh-agent等で利用できる状態にし、次の非対話コマンドが成功することを確認します。

```bash
ssh -o BatchMode=yes -o ConnectTimeout=10 isucon-practice 'hostname; whoami; pwd'
```

秘密鍵はPCに置いたまま使い、チャットやGitに貼り付けません。MyIpCidrはPCのグローバルIPv4 /32を指定し、追加公開ポートは不要です。PCがVPNを使う場合は実際の接続元IPも確認してください。

PCのWork実行環境からSSHクライアント・鍵・SSH設定にアクセスでき、EC2へのTCP/22が許可されている必要があります。通常のターミナルで成功しても、Work側の権限や実行環境が異なる場合があるため、次の手順で確認します。

## 3. MacアプリのWorkからSSH接続を確認する

前節の設定後、手順1で作成したMacアプリのWorkチャットに送ります。

> Macのシェルからssh -o BatchMode=yes -o ConnectTimeout=10 isucon-practice 'hostname; whoami; pwd' を実行してください。
> MacとEC2の結果を区別して報告してください。秘密鍵の内容は表示しないでください。接続に失敗したら設定を変更せず、原因を報告してください。ホスト鍵の検証は無効化しないでください。

EC2のホスト名、ubuntuユーザー、/home/ubuntuが返ることを確認します。ホスト名は環境によって異なります。通常のターミナルでの成功だけでなく、Workからも接続できたことを確認してください。

以降の指示もMacアプリの同じチャットから行います。作業中はMacとアプリを起動したままにし、スリープさせないでください。

### EC2での作業方法

PCのシェルから、各コマンドを明示的にSSH経由で実行します。PCでの `cd` はEC2のディレクトリを変更しません。EC2上の作業ディレクトリはSSHコマンド内で指定します。

```bash
ssh isucon-practice 'git clone https://github.com/rchaser53/2026-10-18-isucon-practice.git ~/isucon-practice'
ssh isucon-practice 'cd ~/isucon-practice && git status --short'
ssh isucon-practice 'systemctl --type=service --state=running'
```

cloneはEC2にまだ配置されていない場合に実行します。PRのマージ前に試す場合は、clone後にEC2で `git switch feat/work-ssh-performance` を実行してください。

実際のISUCONアプリは別ディレクトリです。場所・所有者を調査し、適切なユーザーでファイル編集・サービス操作を行います。ubuntuでSSH接続した場合、別ターミナルの `sudo su - isucon` は後続のSSHコマンドの実行ユーザーを変えません。必要なコマンドだけ適切なユーザーで実行し、アプリ全体の所有者変更や権限緩和は行いません。

ログはSSHで取得し、ファイル転送が必要ならPCからscpを使えます。sudoが必要な操作は権限を確認し、対話入力が必要ならPCで対応してください。

## 4. ベンチの準備と記録

このCloudFormationはアプリ用EC2を1台だけ作り、ベンチマーカーやそのネットワーク設定は作りません。[ISUCON13公式資料](https://github.com/isucon/isucon13)に従い、ベンチ環境・初期化方法・接続先を別途確認してください。実在しないベンチコマンドを固定していません。

ベンチホストにもこのリポジトリを配置し、実際のベンチディレクトリから以下を実行します。WorkからはPCのSSHでそのベンチホストに接続して実行してください。SSHの終了コードとベンチのログは両方確認します。`/absolute/path/to/bench` と引数は実環境のコマンドに置き換えます。

```bash
bash ~/isucon-practice/scripts/benchmark.sh -- /absolute/path/to/bench <実際の引数>
```

Linux、Bash、util-linuxのflockが必要です。スクリプトはコマンドをそのまま実行し、終了コードを維持します。標準出力・標準エラーは画面に流さず、結果ディレクトリに保存します。

| ファイル | 内容 |
| --- | --- |
| metadata.txt | UTC開始時刻、ホスト、作業ディレクトリ、実行コマンド、現在のGit状態 |
| stdout.log / stderr.log | ベンチの標準出力・標準エラー |
| before.txt / after.txt | 実行ホストのuptime、メモリ、ディスクの前後比較 |
| result.txt | 終了コード、経過秒、UTC終了時刻 |

保存先はこのリポジトリの `results/`。同じ保存先を利用する実行をflockで排他し、重複時は75で終了します。`RESULTS_DIR` で保存先を変えられますが、別ホスト・別保存先・直接実行には排他が効きません。チームでベンチホストと保存先を統一してください。終了コード0だけでは競技上の成功を保証しないため、出力のスコアと検証エラーも確認します。

スクリプトのOS情報は**実行ホスト**の情報です。別ホストでベンチを動かす場合、アプリEC2のCPU・I/Oは別途計測してください。アプリ変更のコミットSHAも別に記録します。

## 5. 改善の進め方

1. サービス、アプリの場所、設定ファイル、初期化・デプロイ・ベンチコマンドを調べる。
2. 条件をそろえたベースラインを取得する。appホストで `vmstat 1`、必要ならsysstatの `pidstat` / `iostat` をベンチ時間内に限定して取得する。
3. NginxアクセスログとMySQLスロークエリを対象時間に限定して解析する。既存設定を保存してから計測設定を変更し、終了後に戻す。クエリはEXPLAINで実行計画を確認する。
4. 根拠のある仮説を1つ選び、変更、デプロイ、同条件で再計測する。悪化時はその変更だけ戻す。
5. 最終設定でサービス・EC2を再起動し、起動とベンチ成功を確認する。

t3.mediumはCPUクレジットによって性能が変わります。既存の[構成説明](architecture.md)も確認し、クレジット残量やインスタンスタイプを比較記録に含めてください。同じEC2上でベンチを動かすとリソースを奪い合うため、別ホストの結果と直接比較できません。

比較記録には、日時、アプリのコミット、差分、ベンチ実行先・コマンド、データ初期化条件、計測設定、スコア、エラー、採用・却下の判断を残します。ログにはユーザーデータや認証情報が含まれ得るため、resultsはGit対象外にしています。設定変更前のバックアップも公開リポジトリには置かないでください。

## 6. Workへの最初の指示例

> 接続したPCのシェルからSSHでisucon-practiceに接続し、EC2のISUCON性能改善を進めてください。毎回、ローカル実行とリモート実行を区別してください。最初にEC2でwhoamiとpwd、サービス、アプリと設定の場所、ベンチ環境を調査し、実行手順を記録してください。
> ベンチ環境が未準備なら、その不足を明示してください。準備できたらベースラインとCPU・I/O・アクセスログ・スロークエリを測定し、根拠のある仮説を1つずつ検証してください。
> アプリのコミットと変更差分、スコア、エラーを記録し、悪化した変更だけ戻してください。ベンチは同時実行せず、このリポジトリのscripts/benchmark.shを使ってください。
> 計測設定を元に戻した後、再起動と最終ベンチで動作を確認してください。

## 接続で困ったとき

- Macのシェルが使えない：実行場所が「お使いのコンピューターで」か、ローカル実行の権限があるか確認。
- SSHが通らない：PublicIp、MyIpCidr、鍵、ubuntuユーザーを確認。EC2の停止・起動後はPublicIpが変わる場合があります。
- ターミナルでは通るがWorkでは失敗：Workのシェル、SSH設定・鍵の場所、ssh-agent、ネットワークとファイル権限を確認。
- ファイルが書けない：EC2上の実行ユーザーとファイル所有者を確認。
- 長い計測が切れる：EC2側でtmux等を使って実行を継続し、再接続後に結果を確認。チャットが続いていても、SSHや計測プロセスの継続を保証するわけではありません。

公式資料：[ChatGPT Workの使い方](https://learn.chatgpt.com/docs/get-started-with-work)
